RAG concept map

RAG architecture

RAG combines a retriever and a generator. The retriever finds the best evidence, then the generator uses that evidence to answer with grounding instead of guesswork.

The core idea is simple: search first, then generate.

Core ideas behind RAG

These cards summarize the topic itself: embeddings, retrieval, augmentation, and the limits that shape real-world RAG systems.

Embeddings

Text becomes vectors

Embeddings convert text into numerical vectors so semantically similar passages can be compared in vector space.

Semantic meaning Vector space
Retrieval

Find the best evidence

The retriever ranks chunks by similarity and returns the passages most relevant to the user query.

Top-k search Cosine similarity
Augmentation

Build the prompt with context

Retrieved passages are added to the prompt so the language model can answer with grounded context instead of guessing.

Prompt assembly Grounded answer
Limits

What RAG does not solve

RAG still depends on chunk quality, retrieval quality and prompt design, so it improves generation but does not make it perfect.

Retrieval quality Hallucination risk

RAG in practice

These points connect the theory to the actual use cases: grounded answers, semantic search, vector databases and lower hallucination risk.

01
Grounded answers

RAG adds retrieved evidence to the prompt so the model can answer with support from external documents.

02
Semantic retrieval

Embeddings and cosine similarity help the system find passages based on meaning rather than exact keywords.

03
Vector databases

They store embeddings and make top-k similarity search efficient for the retrieval stage.

04
Limits and tradeoffs

RAG still depends on good chunking, good retrieval and a carefully written prompt to produce reliable answers.
